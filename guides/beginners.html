Part 1

The basics

1

AI roleplay in two minutes

In AI roleplay, a person chats with one or more characters played by a language model: a companion who remembers your day, a crew of thieves planning a heist, a game master running a dungeon. The person writes as their own character; the model writes everyone else.

What happens on every turn

A language model has no memory of its own. Each time it replies, the app sends it everything it needs to know as one long text, called the prompt. The prompt usually holds standing instructions, the character's description, any background facts that matter right now, and the recent conversation. The model writes the next reply; the app shows it to you and adds it to the conversation.

The prompt can't hold everything. Models read a limited amount of text at once, called the context window, measured in tokens (roughly three quarters of a word each). So apps include background facts only when they are relevant, usually when a keyword appears in the recent conversation.

Words you'll meet

TermMeaning
Character cardA file that describes a character so any app can play them: name, description, personality, greetings, example dialogue.
GreetingThe character's first message, which sets the scene. Cards often offer several to choose from.
LorebookA list of background facts, each with keywords. When a keyword appears in the chat, the fact is added to the prompt.
SwipeAsking the model for another version of the same reply, and switching between versions.
BranchGoing back to an earlier message and continuing differently, so the chat forks.
PersonaThe character the person plays, described so the model knows who it's talking to.

Today's character cards, and their limits

Most shared characters today use the Character Card V2 or V3 format, made popular by the SillyTavern chat app and the Chub card-sharing site. A card is a block of JSON (a common plain-text format for structured data), usually hidden inside a PNG picture of the character. It works well for a single companion, but people now use it for much more, and that causes problems:

  • One character per card. Group stories, narrators and settings have to be written as a "character", and greetings can't have their own setup.
  • Lorebooks behave differently in every app. The same card activates different facts in different apps, one of the most common complaints among card creators.
  • No real game mechanics. Health, money, inventories and relationship meters are imitated with text tricks, HTML or app-specific scripts.
  • Group chats leak secrets. In most apps every character sees everything, so a traitor's plan reaches the hero's prompt.
  • Memories are trapped. A companion's memories of you live inside one app and vanish when you move.
  • Fragile sharing. Image hosts often strip the hidden data from the PNG.

Troupe is a new format designed to fix these problems.

2

Troupe at a glance

The name comes from the theater: a troupe is a company of actors who perform many plays. In Troupe, a bundle is the script and the cast, a session is the recording of one performance, and a chronicle is an actor's diary that carries over from one performance to the next.

Six building blocks

Everything in Troupe is built from six ideas:

BlockIn one sentenceChapter
EntriesAny piece of text the model should read when certain conditions hold: lore, rules, secrets, goals, memories.7
VariablesNumbers, flags and lists the story keeps track of, like health, trust or time of day.8
EventsRules that react to the story ("when the twelfth bell rings, close the gates"), or actions players and the model can trigger.9
ConditionsSmall yes-or-no formulas that decide when entries and events apply.10
SessionsThe saved chat, with a record of everything that happened.14
ChroniclesA character's memories carried from one session to the next.17

The smallest possible card

A complete, valid Troupe file can be this short:

{
  "troupe": "0.11",
  "kind": "bundle",
  "characters": [{
    "id": "elena",
    "name": "Elena Voss",
    "description": "A meticulous thief and mapmaker. Calm, exacting, dry humor."
  }],
  "scenarios": [{
    "id": "workshop",
    "openings": [{
      "id": "late",
      "content": [{ "speaker": "elena", "text": "You're late. Sit down, and don't touch the maps." }]
    }]
  }]
}
  • troupe is the version of the format the file follows; kind says this is a bundle.
  • id is a short name that other parts of the file use to refer to Elena. IDs use lowercase letters, digits and underscores, start with a letter, and are at most 64 characters.
  • description is what the model reads to play her.
  • The scenario is what people open. Its openings are greetings: each becomes a first message people can swipe between. With no cast listed, it's one person plus every character in the file: "you and Elena".
  • content is a list of parts, each with an optional speaker. A part without a speaker is narration.
The key principle: save what happenedWhenever something happens in a Troupe session (an entry is added to the prompt, a value changes, a random outcome is chosen), the result is written into the saved chat. Another app opening the session reads what happened and continues from there, without guessing. Dice themselves aren't stored: any app recomputes the same roll from the session's seed (chapter 16).

Part 2

Writing stories

3

Bundles

Bundle
What it is
The file an author shares. It holds any mix of characters, worlds and scenarios, plus information about the work as a whole.
What it's for
Stating credit, ratings and versions once, instead of on every character, and keeping a whole story in one place.
FieldsWhat they're for
id, updated, versionRecognizing the same work across releases. id is shared by all releases and translations; updated (a date) says which release is newer; version is a free label for people, like "1.2".
name, tagline, coverHow the work appears in a library: a title, one line of description, a picture.
authors, creditsCredit: the names shown as the byline, and free text for everything else (license, sources, what it was based on, thanks), written however the author likes. Never sent to the model.
language, tags, rating, warningsFinding and filtering: the language, topics, an age rating (general, mature, explicit), and content warnings in plain words.
creatorNotesNotes for people, such as tips for playing. Never sent to the model.
requiresExtensions the file can't work without, so an app that lacks them refuses the file rather than playing it wrong.
  • A translation is a separate bundle with the same id, another language and every internal ID unchanged, so saved chats work with either.
  • A fork, someone's remix, gets a new id and credits the original in credits, with a link.
  • A lore pack is a bundle with only worlds, which people can add to any chat.
4

Characters

Character
What it is
Anyone in a story, played by the model or by a person.
What it's for
Everything needed to play that person, and everything that travels with them into other stories: their lore and their own variables and events. How a story starts belongs to scenarios, so the same character can join any of them.

Several fields describe the same character for different readers:

FieldWho reads itWhat to put in it
descriptionThe model, whenever the character is in the sceneEverything needed to play them: looks, personality, background, how they talk. Headings like "## Personality" are fine.
summaryThe model, when the character is mentioned but not presentOne or two sentences, so the model knows who people are talking about.
examplesThe modelShort sample exchanges that show the character's voice. char is this character, user the player's.
appearanceImage generatorsOnly what they look like, for consistent pictures. Not sent to the chat model.
voiceSpeech generatorsOnly how they sound, for text-to-speech.
aliasesThe appOther names (a full name, a title), so mentions are recognized.
  • avatar and images are pictures, including expressions such as happy or angry, optionally grouped by outfit (winter/happy).
  • talkativeness (0 to 1) hints how often the character speaks up in a group.
  • The player's own character, often called a persona, is an ordinary character too. It's usually stored in the saved chat rather than the bundle.
5

Worlds and locations

World
What it is
A setting: an always-on overview, places, background facts, and its own mechanics, such as a clock.
What it's for
Sharing one setting between many stories, and keeping setting knowledge out of individual characters.

Locations are places in a world. Each can sit inside another (parent), so "rooftops" can be inside "the Duke's manor". The story always knows its scene: the current location and who is present. The scene decides which characters' lore counts and who witnesses what is said (chapter 13).

6

Scenarios

Scenario
What it is
What people open and play: who is in the story, how it starts, what it's about, and its rules.
What it's for
Combining characters and worlds into a particular story, without changing the characters themselves.
  • premise is the situation, sent to the model. briefing is for the players only ("you are the crew's boss; someone here is lying") and never reaches the model.
  • worlds picks which worlds of the bundle the story uses.

The cast and player seats

The cast lists who takes part. A seat is a place for a person: either an empty seat, which the person fills with their own character when they start, or a character marked player, which the story defines for them (a set protagonist in a dating sim, say). notes add context about a character for this story only, such as "tonight Kai is jumpy". A cast with two seats is a two-player story. A cast member marked spoiler stays out of cast lists until they first appear, so a hidden ghost isn't revealed on the start screen. Without a cast, it's one seat plus every character in the bundle.

Modes: who writes the replies

ModeHow replies are writtenGood for
characters (default)Each model-played character gets their own turn and their own prompt, seeing only what they know.Companions, group chats, secrets that must hold.
narratorOne voice writes the whole scene, all characters included.Text adventures, game masters, novel-style stories.
mixedCharacters take their own turns, and a narrator may add scene description between them.Ensemble stories with atmosphere.

The narrator's style is an ordinary entry in the scenario, placed in "system" and known only by the narrator (chapter 7).

Openings

Openings are the ways a story can start, and they live only in scenarios. People can swipe between them like greetings. Each can start in a different place, with different people present, at a different point in the story, by setting starting values with set, for example {"scene.location": "vault", "bell": 11} (bell is a variable, chapter 8).

  • Written openings have content: the first message, as parts. Several characters can speak in it, each in their own part, with narration parts in between.
  • Starting points leave out content, and the model writes the first message from the setup. A list of them works like a game's start menu: pick your character, then pick "At the tavern", "On the road" or "In the vault", each one line: {"id": "tavern", "title": "At the tavern", "set": {"scene.location": "tavern"}}.
  • Who starts present: the players, plus whoever speaks in a written opening, or the whole cast for a starting point. An opening can also list exactly who is there with scene.present.
7

Entries

Entry
What it is
A piece of text the model reads when its conditions hold. Lore, standing rules, style reminders, secrets, goals, author's notes and memories are all entries.
What it's for
Giving the model the right knowledge at the right moment, without filling the limited prompt with everything at once.
Where it lives
In a world, a character, a scenario, or a saved chat. A character's entries only count while that character is in the scene.

In older formats, lore, instructions and secrets are different things with different rules. In Troupe they are one thing with one set of options. A typical entry:

{ "id": "ship", "keys": ["Kestrel", "ship"],
  "text": "The Kestrel is a patched-up freighter Mira has kept flying for nine years." }

How an entry gets into the prompt

  • No keys: always on. Rules, secrets and goals are written this way.
  • With keys: it activates when one of the words appears in the last few messages (4 by default, set with scanDepth). Keys match whole words, ignoring case, so "war" doesn't match "warship". A key written between slashes, like /dragons?/, is a pattern (a regular expression), for plurals, partial words and similar cases.
  • With when: a condition must also hold, such as "only after the tenth bell" (chapter 10).
  • With pull: the entry is fetched on demand, either requested by the model by its title or found by the app's similarity search (matching by meaning rather than exact words). This suits large lorebooks.
Try it: which entries activate?Mira's card, with six entries

    Where it goes, and who knows it

    • position chooses the part of the prompt: "system" for standing direction such as tone and rules, "context" (the default) for knowledge, or a number for "this many messages from the end of the conversation". Models pay most attention to recent text, so an important reminder can be placed 2 or 4 messages from the end.
    • knownBy lists the characters who know the entry. ["narrator"] means only the narrator sees it. The recipes below show the common uses.

    Timing

    Timing counts in rounds: one player message and the replies to it. That way a story paces the same way in a one-on-one chat and in a busy group.

    • sticky: once activated, stays for this many rounds even without its keyword (as long as its when still holds), so a mood or the weather doesn't flicker.
    • cooldown: after that, it can't activate for this many rounds.
    • once: activates at most once in a story path, for a one-time reveal.
    • chance: a probability from 0 to 1, for occasional color.

    Competition: groups and priority

    • group: at most one entry of a group is used, such as one weather out of rain, fog and clear skies. If several qualify, the highest priority wins; ties are settled by a weighted roll, using weight as the odds (rain 3, fog 1 means rain is three times as likely).
    • priority: 0 to 100, default 50. It decides who wins a group and what is dropped first when the prompt runs out of space (chapter 12).
    • chain: the entry's own text can activate other entries: if one entry's text mentions "the lantern", the lantern entry can activate too.

    Common recipes

    You wantWrite an entry with
    Background lorekeys for the words that bring it up

    A character's secretno keys, knownBy: ["their id"]

    Variables

    Variable
    What it is
    A named value the story keeps track of: a number, a yes-or-no flag, a word from a list, or a set of items.
    What it's for
    Mechanics that models are bad at keeping in their head: health, money, inventories, trust, time, story phases. Declared values are reliable, visible, and the same in every app.
    { "id": "trust", "type": "number", "of": "characters", "min": 0, "max": 1,
  "description": "How much this character trusts {{user}}. Rises when promises are kept; falls on lies.",
  "by": ["model"], "maxStep": 0.2 }

    The description matters: it's written for people and for the model that updates the value, so it should say what the value means and what moves it. initial sets the starting value.

    Types

    TypeHoldsExample
    boolyes or no"the alarm has sounded"
    inta whole numberhealth 0–30, gold
    numbera decimal numbertrust 0.0–1.0
    stringfree textthe name the player chose
    enumone of the words listed in valuesphase: setup, heist, escape
    seta list of distinct wordsan inventory: rope, lantern

    Who can change a variable

    • by lists who besides rules may change a value: "player" (through the app's interface) and "model" (the tracker, chapter 15). Without by, only openings and events can.
    • Guardrails exist because models make mistakes: min and max keep values in range (and can name another variable, like "max": "max_hp"); maxStep limits how much the model can move a value at once; oneWay lets a value only move forward, for clocks and discovered clues.

    Ownership: characters bring their own state

    A variable belongs to whoever declares it. Kai can have his own nerve: inside Kai's own text and conditions it's own.nerve, and everywhere else it's state.kai.nerve. Two characters from different authors can both have a mood without clashing, so characters can be combined into group stories freely.

    More kinds of variable

    • One value per character, of: "characters" gives each model-played character a value (trust toward the player); "cast" includes the players (everyone's health); "others" is everyone but the owner (Kai's feelings toward each person); a list gives named keys (reputation with the watch and the guild); "*" lets keys appear as needed (an inventory with counts).
    • Derived, derive: computed from other values when read, never stored, such as the day number from an hour count.
    • Asked, ask: a question put to the player when the story starts ("How do you want to play this job?"), with labels for nicer choices.
    • Spoiler, spoiler: hidden from the player's screen until the story ends or the player chooses to look, such as who the murderer is.
    • Carried, carry: kept in the character's chronicle and brought into future chats (chapter 17).
    Variables are invisible to the model unless you show themTo let the model see a value, write an entry that mentions it: {"id": "hp", "text": "{{user}} has {{state.hp}} of {{state.max_hp}} health."}. You choose the wording, and with knownBy, who sees it.

    The scene (chapter 5) is state too: scene.location and scene.present, which openings, events, players and the tracker can all change. Characters who aren't present are offstage: the model doesn't read their description or lore, only a short summary if someone mentions them. To keep someone waiting in a room until the players walk in, the specification's pattern C.11 uses one variable for where each character is and one event that updates who's present when the location changes.

    9

    Events and actions

    Event
    What it is
    A rule of the form "when this is true, do that", or an action someone can trigger.
    What it's for
    Story beats, consequences, random encounters, endings, and game moves, without any code.
    { "id": "twelfth_bell", "when": "state.bell >= 12", "once": true, "end": true,
  "message": [{ "text": "The twelfth bell tolls across the harbor. Far below, the gates grind shut." }] }

    When an event fires

    • Events are checked after every player message, after every reply, and when a story starts. when must be true.
    • on: "player" checks only after player messages, before the reply, so the result can shape the reply. on: "model" checks only after replies.
    • once fires at most once; cooldown waits a number of rounds before firing again; chance adds randomness. An event that fires by itself does so at most once per round.

    What an event can do

    FieldEffect
    setSets variables to plain values: {"scene.location": "vault"}.
    computeSets variables to calculated values: {"gold": "state.gold + 10"}.
    messageAdds a narration message to the chat.
    directGives the next reply a one-time instruction, such as "a guard patrol passes below".
    endMarks the story as finished on this path.
    outcomesPicks one of several weighted alternatives each time it fires: a goblin (3 in 4) or an ogre (1 in 4).

    Dice are written roll(20) inside compute. All the rules that fire after one message run in a single, fixed order, and they can't trigger each other in an endless loop.

    Callable events: actions, tools and choices

    An event with call doesn't fire on its own. Instead, it's offered as an action: the model can call it as a tool (a function the app lets the model request), and players can pick it like a menu choice. This is how a game master checks whether a lockpick works, and how a visual novel offers a choice.

    { "id": "pick_lock", "when": "scene.location == 'vault'",
  "call": { "by": ["model", "player"], "label": "Pick the lock",
            "description": "Call when someone tries to open a locked door or chest.",
            "params": [{ "id": "difficulty", "type": "int", "min": 5, "max": 25, "description": "How hard the lock is." }] },
  "compute": { "picked": "roll(20) >= args.difficulty" },
  "direct": "The lock {{state.picked}}. Narrate it." }
    • call.by says who may use it; label is the text players see; description tells the model when to call it.
    • params are the action's inputs, read as args.difficulty; they get the same type checks as variables.
    • It's only offered while when holds, so a lock can only be picked in the vault.
    • picked is a yes-or-no variable declared in the scenario, with the labels "opens" and "holds", so the direction reads "The lock opens."

    Conditions

    Condition
    What it is
    A small formula that is either true or false, written in CEL (Common Expression Language), a small, safe language Google designed for rules like these.
    What it's for
    Deciding when entries apply and events fire, and calculating values, without allowing code that could do anything harmful.

    If you've seen a spreadsheet formula, you can read CEL. == means "equals", && "and", || "or", ! "not", in "is in the list". Text goes in single quotes.

    ConditionIn plain words
    state.bell >= 10The tenth bell has rung.
    scene.location == 'vault' && 'kai' in scene.presentWe're in the vault and Kai is here.
    own.nerve >= 2(Written on Kai) Kai's own nerve is frayed.
    state.trust[char] >= 0.8The character speaking now trusts the player.
    turn % 4 == 0Every fourth round.
    hit('glass') && !hit('guard')"Glass" was mentioned recently, but "guard" wasn't.
    ago('patrol') > 5The patrol last happened more than five rounds ago.
    hour >= 0 && hour < 5It's the middle of the night for the player.
    Everything a condition can read names and what they hold
    NameHolds
    state.x, state.kai.x, own.xVariables: a scenario's, a character's, the expression owner's own.
    scene.location, scene.present, scene.withinWhere we are, who is here, and every place we're inside.
    turnHow many rounds have passed.
    char, user, self, playersWho is being written for, the player's character, who owns this rule, all players.
    opening, scenarioWhich opening and scenario are being played.
    last.from, last.charWho wrote the latest message.
    elapsed, hour, weekdaySeconds since the previous message; the player's local hour and day.
    count(name), ago(name)How often, and how many rounds ago, an event fired, an entry activated or a value changed.
    hit(word)In entries: whether a word appears in the recent messages.
    roll(n), args.xIn events: a die from 1 to n; an action's inputs.
    min, max, abs, size, contains…A short list of standard functions.

    Apps check every condition when they load a file, so typos are reported up front. A condition that fails while playing counts as false.

    11

    Macros

    Macro
    What it is
    A placeholder in double braces that the app replaces with a name or value when the text is shown or sent.
    What it's for
    Writing text once that works for any player, any character and any moment of the story.
    You writeThe reader sees
    {{char}}The character the text belongs to, or the one being written for
    {{user}}The player's character
    {{@kai}}Kai's name (@ turns an ID into a name)
    {{state.bell}}, {{own.nerve}}A variable's value, or its label if it has one
    {{@scene.location}}, {{@scene.present}}The current place's name; the names of everyone present
    {{pick::red::blue::green}}One option, chosen once and kept for the whole chat
    {{// a note}}Nothing: a comment for authors
    Macros never work in what players and models writeOnly author-written text is expanded. If a model wrote {{state.culprit}} in a reply, it stays as plain text. Otherwise a model, or a malicious instruction hidden in the chat, could reveal hidden values by typing a macro.

    Part 3

    Playing a story

    12

    A turn, step by step

    1. A player writes, or picks a choiceChoices are callable events offered to the player.
    2. Rules runEvents that apply after player messages run before anyone replies, so one marked on: "player" can roll for what the player attempted.
    3. Entries activateKeywords, conditions, timing and groups decide which entries to include, the same way in every app.
    4. The prompt is assembledInto five slots, shown below.
    5. The model repliesAs plain text, or as structured data with speakers, changes and actions (chapter 15).
    6. The tracker updates stateA model reads the reply and updates the values it's allowed to change.
    7. Rules run againAfter the reply and its tracking, events react: change values, add narration, direct the next reply, or end the story.

    The five slots of a prompt

    When space runs out, the app drops entries below priority 100, lowest priority first; if the priority-100 entries alone don't fit, the reply fails rather than lose them. How an app shortens examples and old history is its own choice; the saved chat never changes.

    13

    Who knows what

    Real stories depend on people not knowing things: the traitor's plan, the whisper in the corridor, what happened while you were away. Troupe tracks this with two rules.

    • The witness rule: a line is known by its speaker and by everyone present when it happens, including someone who arrives or leaves in that message. Characters who weren't there don't know it, without anyone marking it up.
    • knownBy: narrows a line or entry to only the listed characters, for whispers, thoughts and secrets.
    Try it: see the story through someone's eyesA moment from the heist

    Who is being written forWhat they see
    A character (characters or mixed mode)Only what that character knows.
    The narrator in mixed modeEverything, except content whose knownBy lists characters but not the narrator.
    The single voice in narrator modeEverything, with restricted content marked ("Known only to Kai:").
    The people playingEverything, apart from spoiler values until the end. Knowledge limits what models see, not what people can read.
    14

    Sessions

    Session
    What it is
    The saved chat: a header (which scenario, who's playing, the dice seed, the players' limits) and one line per message.
    What it's for
    Saving everything that happened, with enough detail that any app can continue where another left off.
    An exchange format, not a databaseApps store chats however they like. This format is how a chat moves between apps: export, backup, sharing a playthrough. Like a chess game in standard notation, it's a common language, not storage.
    • A tree, not a list. Swipes and branches are siblings under the same parent, and each opening is its own root, so greetings can be swiped too.
    • The head is the message you're currently at; the story so far is the path from a root to it.
    • Branches never share state: health lost on one branch is still intact on the other.
    • Appendable. Apps can save by adding lines instead of rewriting the file, which makes autosave cheap and crash-safe.
    • The bundle is never changed by play. A chat's state is the starting values plus the changes recorded along its path; apps may cache it however they like.
    • Recasting. A session can carry its own version of a character under the same ID, which replaces the bundle's for that chat: a different character in the same part, or an edited copy. Everything that refers to the character keeps working, and text that names other characters as {{@kai}} rather than "Kai" shows the new name.

    What each message records

    FieldWhat it's for
    contentThe message itself: text, images, audio, with speakers.
    from, char, authorWritten by a player, the model or the system; which character it was written for; which person wrote it.
    changesThe variable changes it caused, and which rule or action made them.
    activatedWhich entries newly activated for it.
    entriesEntries added from this point on: an author's note, a memory, a fact learned.
    summaryA short summary of earlier messages, which can stand in for them when space is tight.
    pinned, hidden, stoppedRepeated in the prompt's Context slot; kept for people but never sent to the model; a reply that was cut off.
    15

    The model's reply as data

    Every saved message is a list of parts, each with an optional speaker. Models usually return plain text, though, so how does a reply become parts?

    Plain replies: the usual case

    In characters mode, each reply is one character's turn, so the app already knows who is speaking. It stores the whole reply as one part spoken by that character. Actions, scene description and thoughts stay inside the text, the way people write them today:

    *Kai hesitates, glancing at the harbor.* Fine. Your plan, boss. For once.

    No special output is needed. The one thing plain text can't do is keep a thought private: apps never guess from the text who knows a line, so everyone present counts as having witnessed the whole reply.

    Structured replies: when you need them

    Two situations need the model to return parts itself: one reply that voices several characters (as in narrator mode), and content only some characters should know, such as a private thought. Then the reply is data:

    { "parts": [
    { "text": "The seventh bell rolls across the harbor." },
    { "speaker": "kai", "text": "*Kai nods.* Fine. Your plan, boss." },
    { "speaker": "kai", "knownBy": ["kai"], "text": "*If the Duke's men are early, this ends badly.*" }
] }

    The same package can also carry value changes, new memories, newly introduced characters and actions the model wants to call.

    The tracker

    Values can change with either kind of reply. The tracker is a separate, often cheaper model call that reads the latest messages, along with each variable's description, range and current value, and reports only what changed. Its changes pass the same guardrails as everything else. Entries placed "tracker" give it extra guidance.

    Conditions in plain wordsTo react to something hard to detect, like "Elena has told the crew about the key", make it a yes-or-no variable that the model may set and that only moves forward (oneWay), with that sentence as its description. The tracker flips it when it happens, and from then on it's a recorded fact.
    16

    Dice you can trust

    Random choices (which weather, which monster, a dice roll) must come out the same in every app that replays a chat, and must change when you ask for a new version of a reply. Troupe does this with a recipe instead of a random number generator: it mixes the session's random seed, the message's ID and what is being decided into a fingerprint (a SHA-256 hash), and reads a number from it.

    Try it: roll the weatherRain has weight 3, fog weight 1
    Computing…

    Try message 3 and then 4: they're two versions of the same reply, so each gets its own roll. Fog for one, rain for the other, in every app.

    17

    Chronicles

    Chronicle
    What it is
    A file that carries one character's continuity: their current definition, their memories, and values like closeness, across chats and across apps.
    What it's for
    Companions who remember you. It's what you keep of "my Mira after a year", and you can take it with you.
    • Mark a character's variables and memory entries with carry to keep them in the chronicle.
    • Memories are ordinary entries, usually with pull and a title, so thousands of them can exist without crowding every prompt.
    • People can read, edit and delete every memory. Deleting a message can prompt the app to forget memories that came from it.
    • A long friendship can run as many short chats with one chronicle, instead of one endless chat.
    18

    Media, limits and safety

    • Audio messages are parts with a transcript, which is what text models read and what lore keywords match against.
    • Generated media records how it was made (generated: which model, prompt and seed), and apps keep media files unchanged, so authenticity labels embedded in them survive.
    • Player limits: the people playing can set lines (never show this) and veils (may happen, but only offscreen). Apps apply them to every generation, images and voice included, and never drop them to save space.

    Built-in safety for shared files

    RuleWhy
    No scripts, no raw HTMLA shared card must never run code; a script in a card could steal the keys to your AI account.
    No silent downloadsA remote image lets its owner see when and where a card is opened; apps ask first.
    Pictures only in safe formats (no SVG)Some image formats can carry scripts.
    Safe patterns and conditionsPatterns run in linear time and conditions are sandboxed, so neither can run away with the app.
    Safe archive handling, size limitsA malicious package can't overwrite files or exhaust memory.
    Story text is never an instruction to the appLore and replies are content, not commands.

    20

    Compatibility and growth

    • Two levels. A Core app supports everything except variables and events (and openings that set values other than the scene), which is enough for imported cards and lorebooks. A Full app supports mechanics too. An app that can't play a file properly refuses it, rather than telling a different story.
    • Extensions. Apps can add their own data under ext, keyed by name, and every other app keeps it safe when saving. requires marks extensions a file depends on.
    • Versions are compared as two whole numbers, so 0.10 is newer than 0.9. From 1.0, minor versions only add things older apps can safely ignore; before 1.0, any version may break, so apps fully support only their own and warn about the others.

    A full example, explained

    The Lantern Heist is the example story in the specification. The player, as the crew's boss Mara, has hired two thieves to steal a duke's storm lantern before the harbor bells ring twelve.

    PieceIn the heist
    CharactersElena, a meticulous planner with a secret entry: she still has the vault's master key. Kai, a reckless acrobat with a secret deal with the Duke, his own variable nerve, and a style reminder only he sees.
    WorldPort Veyra, with the manor, its rooftops and the vault; lore about the storm lantern; a weather group of rain (weight 3) and fog (weight 1), sticky 6, cooldown 4.
    Variablesbell, a one-way clock from 6 to 12 the model advances; trust per character, a spoiler; approach, asked at the start; two plain-words flags.
    EventsA rooftop patrol after player messages, with weighted outcomes that direct the reply; Kai's confession costing Elena's trust; the twelfth bell ending the story.
    Openings"Rooftop briefing", and "Already caught", which starts in the vault at the eleventh bell, without Kai.

    The first four messages

    1. Opening: rooftop briefingThe first message records the starting location and who's present (Mara, Elena, Kai), then the player's answer to "how do you want to play this job?" (quietly).
    2. Mara: "We wait for the eighth bell. Kai, you take the east stair."A player message, the start of round 1. The patrol can't fire yet: it waits until after round 2.
    3. Kai replies: "East stair. Sure." and slips awayGenerated for Kai. The weather roll for this message picked fog, so the prompt held the fog, Kai's voice and secret deal, the style rule and the bell clock. Afterwards the tracker records that Kai left the scene and that his nerve rose to 1.
    4. Or, swiped: Kai hesitates, then agreesA second version of the same reply has its own ID, so its own weather roll: rain this time. The tracker records the seventh bell and Kai's trust rising to 0.5. Kai's private worry is known only to him, and a new memory entry notes he was given the post nearest the trap.

    On the first branch Kai has left, so by the witness rule he won't hear what Elena and Mara say next. On the second he stays. Any app opening this session sees the same state on each branch, without re-running anything.

    Status and road to 1.0

    Version 0.11 is a draft; breaking changes are allowed until 1.0. Troupe is specified in two documents: Format defines the files, and Play defines how apps play them. A conformance suite checks implementations against both. Appendix G of Format lists what 1.0 still needs and the extensions planned after it.

    Reference

    Glossary

    Activation
    An entry being included in a prompt. Recorded in the message's activated list.
    Branch
    A different path from an earlier message; branches never share state.
    Bundle
    The file an author shares, holding characters, worlds and scenarios.
    Callable event
    An event offered as an action that the model or players can trigger.
    Cast
    Who takes part in a scenario, including player seats.
    CEL
    Common Expression Language: the small, safe formula language used for conditions.
    Character card
    A file describing a character so any app can play them; Character Card V2/V3 is today's common format.
    Chronicle
    A file carrying one character's memories and values between chats.
    Context window
    How much text a model can read at once.
    Core / Full
    The two levels of app support: Core plays cards and lore; Full adds variables and events.
    Entry
    Text the model reads when its conditions hold.
    Event
    A rule that reacts to the story, or an action someone can trigger.
    Greeting
    A character's first message; in Troupe, an opening.
    Head
    The message a chat is currently at.
    knownBy
    The list of characters who know an entry or a line.
    Lorebook
    In older formats, a list of facts with keywords; in Troupe, entries.
    Macro
    A {{placeholder}} replaced with a name or value in author-written text.
    Offstage
    Part of the cast but not present in the current scene.
    Opening
    A way a scenario starts: a written first message, or a setup the model writes from. Several can be swiped between.
    Persona
    The character a person plays.
    Pinned
    A message repeated in every prompt while it stays on the path.
    Prompt
    Everything the app sends the model for one reply.
    Pull
    Fetching an entry on demand, by the model or by similarity search.
    Recasting
    A session replacing a bundle character with another under the same ID.
    Round
    One player message and the replies to it; the unit Troupe counts durations in.
    Scenario
    What people open and play: cast, openings, rules.
    Scene
    Where the story is and who is present.
    Seat
    A place in the cast for a person.
    Seed
    A random value per session that makes every roll reproducible.
    Session
    A saved chat, with every outcome recorded.
    Slot
    One of the five parts of a prompt: System, Setting, People, Context, History.
    Swipe
    Another version of the same reply, stored as a sibling message.
    Token
    The unit models read text in, roughly three quarters of a word.
    Tracker
    A model call that reads the story and updates variables.
    Variable
    A value the story tracks, with a type and rules about who can change it.
    Witness rule
    A line is known by its speaker and whoever is present when it happens, including people arriving or leaving in that message.
    World
    A shared setting with locations, lore and its own mechanics.
